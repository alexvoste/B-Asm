## 📦 Description

Welcome back, you already know now crutical testing is for projects. The main key things testing lets you catch are bugs when using a module, race detection, coverage, and full logging of everything going on so you can trace the execution.

The ForgeZero project has all kinds of tests, and as you can see in some modules there's more test files than actual logic files.

We're all about load (stress) tests, mocks, and unit tests here.

---

If you wanna become a contributor to the project, it's super important to understand that when you're building a new module, you gotta cover it with tests - pick the one that handles it best and catches issues before you even send that PR lemme break down the most important ones now.

> [!IMPORTANT]
> To begin using the test tooling, ensure that Go (Golang) is installed on your target device—preferably the latest stable release.

Installation on Arch Linux(pacman) or others arch-based linux systems:

```bash
sudo pacman -S go
```

📒 Other Distributions and Environments
For Debian/Ubuntu-based systems, use apt; for Fedora/RHEL, use dnf or yum; for macOS, use Homebrew; for Windows, use the official MSI installer or Chocolatey. Alternatively, download the precompiled binary distribution from the official Go website and configure your PATH accordingly.

> [!CAUTION]
> Critical Prerequisite: Build Toolchain
> To ensure reliable test execution, all core build tools must be present in your environment. Incomplete toolchain installation will cause tests to fail or produce unreliable results.
> If your development work is limited to a single module and does not involve cross-cutting changes, you may install only the subset of tools strictly required by that module.

### 🪚 Mandatory Tooling:

- Tool Minimum / Recommended Version
- GCC 16.1.1+ (any version acceptable)
- Clang 22.1.8+ (any version acceptable)
- NASM 3.02 (any version acceptable)
- FASM 1.73.35 (any version acceptable)

Version constraints are non-strict—later releases are expected to work.

**Zig** – version 0.16.0 (note: still pre-1.0). This is a hard dependency for cross-compilation workflows. Furthermore, ForgeZero—the project's build system—uses zig cc and zig c++ as its default C/C++ compiler backends.

## 🛠 Description of the primary test commands.

### Key commands:

1. go test -v ./... – Executes all tests in the current module and its subpackages with verbose output enabled.

2. go test -race ./... – Runs all tests with the Go race detector activated to identify data race conditions.

3. go test ./... – Runs all tests in the standard (non-verbose) mode across the entire module.

4. go test ./... -cover – Executes all tests and reports code coverage metrics for the tested packages.

📄 To run an individual test case, assume you have written a module named subpackages. This module contains the implementation files and their corresponding test files: `subpackages.go` and `subpackages_test.go.`

If you wish to execute a specific test function for verification purposes, use the following command:

```bash
go test -v ./internal/subpackages -run YourNameForTestOption
```

Test Coverage Targets

Based on the coverage report generated by go test ./... -cover, the following guidelines apply:

    All packages with existing test coverage should not regress below their current percentages.

    For packages currently at 0.0% coverage (e.g., cmd/fz/buildcmd, internal/pyzero, internal/seal, etc.), the goal is to introduce meaningful tests to bring coverage above zero where feasible.

    Packages with coverage already at or near 100% (e.g., internal/iso/core, internal/man, internal/updater/rollback) should remain at that level.

    The overall directive is: prefer to increase coverage; never decrease it.

Coverage refers to test coverage — a metric that quantifies the extent to which the source code of a program is executed when the test suite is run. In the context of Go, it is typically measured as the percentage of statements in the codebase that are exercised by the tests.

**More specifically:**

    Statement coverage indicates the proportion of executable statements that are actually invoked during test execution.

    Higher coverage generally implies that more of the code has been verified, which reduces the likelihood of undetected bugs — although it does not guarantee correctness, as it says nothing about the quality or thoroughness of the assertions made in the tests.

    In Go, coverage is reported by the built-in testing tool using the -cover flag, which instruments the binary during test execution and produces a coverage percentage per package.
